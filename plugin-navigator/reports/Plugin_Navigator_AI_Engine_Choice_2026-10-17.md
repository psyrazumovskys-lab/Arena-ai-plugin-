# Plugin Navigator — выбор ИИ под железо Xeon E5-2666 v3 + GTX 1060 3 ГБ

**Дата:** 17 октября 2026
**Контекст:** ветка `arena/01a0cb29` (Plugin Navigator 2.7.0, встроенный WebLLM 0.2.84 + Qwen3.5-2B-q4f16_1). Вопрос: какой ИИ-движок и модель оптимальны для рабочей машины пользователя.

---

## 1. Резюме (TL;DR)

| Вопрос | Ответ |
|---|---|
| Модель остаётся Qwen3.5? | **Да** — лучший русский язык в малом классе, выбор 2.7.0 подтверждён |
| Текущий вариант Qwen3.5-2B-q4f16_1 на GTX 1060 3GB | **Под вопросом**: 2245 МБ из ~2800 доступных + FP16-вычисления на Pascal в 64 раза медленнее FP32. Нужен живой тест и обязательный fallback |
| Безопасный вариант для этой карты (WebLLM) | **Qwen2.5-1.5B-Instruct-q4f32_1** (1889 МБ, FP32-путь) или **Qwen3.5-0.8B-q4f32_1** (1894 МБ) |
| Лучший вариант «для себя» | **Ollama** (официально поддерживает GTX 1060) + `qwen3.5:4b` — качество заметно выше 2B |
| Стратегический вариант для 2.8.0 | **llama.cpp Vulkan-сборка** (30,8 МБ, работает на Pascal БЕЗ CUDA, для генерации на 1060 Vulkan даже быстрее CUDA) + CPU-fallback на AVX2-ядре Xeon |

## 2. Аппаратный аудит

### 2.1 CPU — Xeon E5-2666 v3

- 10 ядер / 20 потоков, Haswell-EP (2014), 2,9–3,5 ГГц, 25 МБ кэша;
- **AVX2 есть, AVX-512 нет** — для llama.cpp это норма: «AVX512 бесполезен, AVX2 достаточно» (llama.cpp discussion #11765);
- платформа X99: **четырёхканальная DDR4**. Если установлены 4 модуля — ~59 ГБ/с пропускной способности, если 2 — ~30 ГБ/с. Это главный фактор скорости CPU-инференса: генерация токена упирается в пропускную способность памяти, а не в ядра;
- 32 ГБ RAM — достаточно для любых моделей до ~30B Q4; для задач справочника с огромным запасом.

### 2.2 GPU — GTX 1060 3 ГБ: четыре критических факта

1. **Pascal (GP106, compute capability 6.1), 3 ГБ GDDR5, 192 ГБ/с** — по пропускной способности карта отличная: 1B-модель считает быстрее 90 ток/с (Vulkan). Проблема не в скорости, а в объёме и FP16.
2. **FP16-арифметика на Pascal работает в 1/64 скорости FP32** (подтверждение NVIDIA Developer Forums: все CC 6.1 — GTX 1050/1060/1070/1080 — имеют low-rate FP16). Вывод сообщества: «FP16 на Pascal ужасно медленный; llama.cpp с FP32-вычислениями — то, что Pascal умеет хорошо» (r/Oobabooga). Поэтому варианты **q4f16 на этой карте — зона риска**, а **q4f32 — правильный путь**.
3. **CUDA 13 выбросила Pascal** (sm_61 удалён без предупреждения; в CUDA ≤12 Pascal остался только как PTX с JIT-компиляцией при первом запуске). Современные сборки llama-cpp-python cu125 для 1060 падают с ошибкой (issue abetlen/llama-cpp-python #2234). **Vulkan-бэкенд не затронут и на 1060 для генерации токенов даже быстрее CUDA** (llama.cpp issue #19817: 1B Q4 tg128 — Vulkan 90,6 ток/с против CUDA 61,7).
4. **Драйверы**: Game Ready-поддержка Pascal закончилась в октябре 2025, до октября 2028 — только критические обновления безопасности. Для WebView2/Vulkan карта полностью работоспособна; для Ollama требуется драйвер 570+.

### 2.3 Реальный бюджет VRAM

Из 3072 МБ карты Windows + браузер/WebView2 съедают ~200–400 МБ. **Рабочий бюджет для модели: ~2500–2800 МБ**, и то при условии, что параллельно не запущено что-то тяжёлое. При превышении D3D12 молча выгружает часть буферов в системную память — модель «работает», но скорость падает в разы.

## 3. Проверка текущего решения 2.7.0 (WebLLM + Qwen3.5-2B-q4f16_1)

Данные реестра WebLLM 0.2.84 (извлечены из пакета `@mlc-ai/web-llm` на npm, поле `vram_required_MB` уже включает KV-кэш при контексте 4096):

### 3.1 Модели, влезающие в 3 ГБ карту

| Модель | VRAM | Путь вычислений | Вердикт для 1060 3GB |
|---|---|---|---|
| gemma3-1b-it-q4f16_1 | 711 МБ | FP16 | Если shader-f16 доступен — отлично; многоязычная, но 1B |
| Llama-3.2-1B-q4f32_1 | 1129 МБ | FP32 | Русский слабый |
| Qwen2.5-0.5B-q4f32_1 | 1060 МБ | FP32 | Слишком мала |
| Qwen3-1.7B-q4f16_1 | 2037 МБ | FP16 | Риск FP16-скорости на Pascal |
| **Qwen2.5-1.5B-q4f32_1** | **1889 МБ** | **FP32** | **Безопасный выбор — рекомендую как fallback-дефолт** |
| Qwen3.5-0.8B-q4f32_1 | 1894 МБ | FP32 | Совсем новая генерация, 0.8B |
| Qwen3.5-2B-q4f16_1 (текущая) | 2245 МБ | FP16 | 80% бюджета карты + риск №1 и №2 из §2.2 |
| Qwen3.5-2B-q4f32_1 | 2592 МБ | FP32 | Не влезает (93% бюджета) |
| Qwen3.5-4B-q4f16_1 | 3868 МБ | FP16 | Не влезает |

### 3.2 Вывод по текущему решению

- На современных GPU (Turing и новее) Qwen3.5-2B-q4f16_1 — правильный выбор, менять не нужно.
- На GTX 1060 3 ГБ возможны три сценария: (а) не хватит VRAM → WebLLM откажет; (б) shared-memory spill → ответы по минуте; (в) FP16-шейдеры без аппаратного ускорения → катастрофическая просадка. Какой из трёх реализуется — покажет только живой тест (в песочнице WebGPU нет).
- WebGPU на Pascal в Chromium/WebView2 **работает** (замер на GTX 1050 Ti, Edge 143: модель 1.2B — ~15 ток/с) — т.е. сама технология применима, вопрос только в кванте и VRAM.
- У WebLLM **нет CPU-fallback**: нет WebGPU — нет ИИ (WASM-путь даёт 1,6 ток/с даже на 360M — непригодно).

## 4. Альтернативные движки

### 4.1 Ollama — лучший вариант «поставить и пользоваться» на этой машине

- **Официальная поддержка GTX 1060 подтверждена** таблицей в `docs/gpu.mdx`: compute capability 6.1, требование — драйвер 570+ (у Pascal security-ветка это удовлетворяет).
- 3 ГБ VRAM: `qwen3.5:2b` Q4 (~1,3 ГБ) помещается целиком → десятки ток/с; `qwen3.5:4b` Q4 (~2,5 ГБ) — впритык, при нехватке Ollama сама разнесёт слои между GPU и CPU; `qwen3.5:9b` и больше — гибрид или чистый CPU.
- Минус для конечных пользователей программы: Ollama — сторонняя установка; для себя — не проблема.

### 4.2 llama.cpp — стратегический движок для Windows-сборки 2.8.0

Официальные Windows-сборки b11714 (октябрь 2026):

| Сборка | Размер | Для 1060 |
|---|---|---|
| `bin-win-vulkan-x64.zip` | **30,8 МБ** | **Да — без CUDA-рантайма, работает на Pascal** |
| `bin-win-cuda-12.4-x64.zip` + cudart | 255 + 373 МБ | Работает (Pascal через PTX+JIT), тяжело и медленнее Vulkan на генерации |
| `bin-win-cuda-13.4-x64.zip` | 148 МБ | **Нет — Pascal удалён из CUDA 13** |
| `bin-win-cpu-x64.zip` | ~5 МБ | Да, AVX2 на Xeon |

Архитектура: Neutralino-приложение запускает `llama-server` (OpenAI-совместимый HTTP API на localhost), фронтенд общается с ним как с обычным API. Веса GGUF загружаются кнопкой, как сейчас у WebLLM. Преимущества:

- нет зависимости от WebGPU и shader-f16 — работает на любой карте 2016+ и на чистом CPU;
- правильная FP32-математика для Pascal через Vulkan;
- авто-fallback Vulkan → CPU силами самого llama.cpp (`--device` / `-ngl`);
- открыт весь GGUF-зоопарк моделей, включая русскоязычные тонкие настройки;
- для HTML-версии справочника WebLLM остаётся как есть.

Риски: управление процессом из Neutralino, ложные срабатывания антивируса на неподписанный exe, чуть больший объём дистрибутива (~+31 МБ).

### 4.3 WASM-движки (wllama)

Отпадает: 1,6 ток/с на модель 360M — на 1,5B+ непригодно в принципе.

### 4.4 Облачные API

Противоречит концепции продукта (офлайн, без ключей, приватность) — не рассматриваем для публичной сборки. Как личная опция — всегда можно, но не тема этого отчёта.

## 5. Ожидаемые скорости на этом железе

Оценки по аналогам (Vulkan-бенчмарки 1060, WebGPU-замер 1050 Ti, CPU-формула «пропускная способность / размер весов»; помечены ~ как оценочные):

| Путь | Модель | Скорость генерации | Комментарий |
|---|---|---|---|
| WebGPU/WebLLM | 1,2–2B Q4 | ~12–20 ток/с | по аналогии с 1050 Ti (14,7 ток/с на 1.2B), 1060 быстрее |
| Vulkan llama.cpp | 1B Q4 | ~90 ток/с | замер issue #19817 (1060 6GB) |
| Vulkan llama.cpp | 2B Q4 | ~40–55 ток/с | оценка масштабированием |
| Vulkan llama.cpp | 4B Q4 | ~15–22 ток/с | частично может уйти в RAM |
| CPU (4-канальная DDR4) | 2B Q4 | ~15–20 ток/с | ~45 ГБ/с эфф. / 1,3 ГБ весов |
| CPU | 4B Q4 | ~8–12 ток/с | |
| CPU | 8–9B Q4 | ~4–7 ток/с | потолок качества, медленно |
| CPU (2-канальная DDR4) | всё выше | ÷2 | проверить число модулей RAM! |

Для справочника, где ответ — 150–300 токенов, всё до ~10 ток/с включительно юзабельно (15–30 с на ответ). Prefill контекста 2–3 тыс. токенов на CPU добавит 10–30 с на больших моделях; на 2B — единицы секунд.

## 6. Рекомендация: трёхуровневый план

### Уровень 1 — патч 2.7.1 (малые усилия, большая польза)

Добавить в существующий WebLLM-модуль:

1. **Детект возможностей** при первом запуске ИИ: `adapter.info`/`limits` → бюджет VRAM, наличие `shader-f16`;
2. **Цепочка fallback**: если VRAM-бюджет < ~2,4 ГБ или shader-f16 недоступен → предложить `Qwen2.5-1.5B-q4f32_1` (1889 МБ) вместо `Qwen3.5-2B-q4f16_1`; при полном отказе WebGPU — внятное сообщение вместо молчания;
3. Выбор модели пользователем в разделе ИИ (с подписями «для слабых GPU» / «рекомендуется»).

Это же решает проблему остальных пользователей со старыми картами и ноутбучными iGPU.

### Уровень 2 — Ollama-коннектор (лучшее для личного использования)

Опция «Подключиться к Ollama» в разделе ИИ: фронтенд проверяет `http://127.0.0.1:11434` и при наличии использует его вместо WebLLM (API простейший, CORS настраивается `OLLAMA_ORIGINS`). На вашей машине:

- `ollama pull qwen3.5:2b` — мгновенные ответы целиком в VRAM;
- `ollama pull qwen3.5:4b` — заметно умнее, гибридная разгрузка, ~10–20 ток/с.

### Уровень 3 — v2.8.0 на llama.cpp Vulkan (стратегически)

Встроить `llama-server` Vulkan (30,8 МБ) в Windows-сборку как основной движок, WebLLM оставить для HTML-версии. Убирает зависимости от WebGPU/WebView2-обновлений, даёт FP32-математику для Pascal и честный CPU-fallback. Совместимо с текущей архитектурой загрузки модели по кнопке.

## 7. Чек-лист проверки на живой машине

1. `chrome://gpu` / `webgpu-report` в Edge: есть ли WebGPU-адаптер и `shader-f16`;
2. Загрузка Qwen3.5-2B-q4f16_1 в текущей 2.7.0: стартует? скорость? (это ответ на вопрос «повезёт или нет»);
3. Тот же тест с Qwen2.5-1.5B-q4f32_1 (после Уровня 1);
4. CPU-Z / `wmic memorychip`: сколько каналов RAM (2 или 4 модуля);
5. Драйвер NVIDIA: версия ≥ 570 (для Ollama);
6. `ollama run qwen3.5:2b` — замер скорости; сравнить с WebLLM;
7. При желании: `llama-bench -m qwen3.5-2b-Q4_K_M.gguf` из Vulkan-сборки llama.cpp — эталонная цифра.
